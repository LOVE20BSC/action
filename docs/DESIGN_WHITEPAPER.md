# LOVE20 Action 设计白皮书

本文说明整个 `action` 代码库的职责、接口、资金流、轮次、约束和失败处理，面向治理提案发起者、参与者及前端开发者。规则依据本仓 `src/` 和实际调用的 core 接口整理；不把外部规格、旧审查报告或部署示例当作规则来源。所有代币数量均以最小单位计，比例精度除特别说明外均为 `1e18`，除明确向上取整处外，整数除法向下取整。

## 1. 范围与模块

| 模块 | 职责 |
| --- | --- |
| `ActionTarget` | 接收 core 提案和投票回调，固定行动与执行器的绑定，记录公共参与状态，路由行动奖励 |
| `ExecutorBase` | 从 core 推导依赖地址，提供身份与回调权限检查、领取窗口和批量领取 |
| `LpExecutor` | 托管 LP，以有效参与数量和最新治理占比计算奖励及溢出销毁 |
| `GroupActionExecutor` | 群行动的公共入口、索引和个人奖励结算 |
| `GroupActionManager` | 行动初始化、群激活与停用、群配置、激活质押和参与额度 |
| `GroupActionJoin` | 自有参与、资助额度、退出退款、验证资料及成员历史 |
| `GroupActionVerify` | 验证者申请、唯一验证者选举、验证评分、履约判断与退押扣罚 |
| `GroupActionStorage` | 群行动各模块共享的存储与固定限制 |
| `GroupServiceExecutor` | 按群行动的有效产出，为验证者及群主分配服务激励 |
| `GroupRecipients` / `GroupServiceStorage` | 群主服务奖励的收款配置、二次分配、历史和结算缓存 |
| 各 `*RoundAxis` | 把 core 当前 phase 换算为行动的加入、验证或领取轮次 |
| `MemberOwner` | 查询 NFT 当前所有者，并处理身份不存在的情况 |
| `src/interfaces/` | 本仓公共结构、函数、错误和事件的接口定义 |
| `script/deploy/` | 部署、依赖交叉检查、字节码检查和源码验证 |

行动以 `(tokenAddress, actionId)` 标识，`actionId` 是创建行动的 core 提案 ID。不同社区、不同提案的资金和业务记录分别记账。同一执行器可以处理多个行动，执行器地址本身不是行动 ID。

本仓不实现 core 的治理票生成、提案资格、社区代币发行总规则，也不实现群聊消息或群聊管理器；这些不应从本白皮书推导。

## 2. 身份、权限与信任边界

成员身份是 `MemberNFT` 的 `memberId`。`groupId`、`verifierId`、资助者和收款人也使用这套身份。需要所有者权限的操作检查调用时的 NFT owner；身份转让后，操作权、退款接收权和奖励领取权随之转移。本仓不额外要求 `groupId` 来自某个特定群聊管理器。

核心权限如下：

- 只有绑定的 core `Submit` 可以发送创建和提案提交回调；只有 core `Vote` 可以发送投票回调。
- 执行器的 core 回调只接受其 `ActionTarget`。
- 只有某行动绑定的执行器可以修改该行动的公共加入登记、领取该行动的整笔提案奖励。
- 个人参与、申请、停止、撤回与领取由相应 memberId 的当前 owner 操作；群配置与收款配置由 groupId 当前 owner 操作。
- 用户资金入口与领取入口使用重入保护；只读查询不产生结算。

创建时，`ActionTarget` 校验执行器有代码且它的 `ACTION_TARGET_ADDRESS()` 指回自己。这里没有官方执行器白名单：选择执行器是提案和参与者必须评估的信任决策。行动绑定后，没有切换执行器或修改固定初始化参数的入口。

`forceClearJoinState` 是公共参与登记的紧急清理入口，**只清登记，不移动执行器内的本金，也不等于强制退款**。执行器自己的余额和退出规则仍然存在，不能把公共登记当作唯一资金账本。

## 3. 统一轮次

`phase` 是 core 当前阶段编号。一个 phase 同时服务多个不同的行动轮，并非所有业务使用同一个 `round`。

| 行动轮 R 的工作 | 发生时的当前 phase |
| --- | --- |
| 创建行动、再次提交提案、治理投票、选举验证者 | R |
| 加入、追加、退出等参与数量变更 | R+1 |
| LP 奖励开始可领 | R+2 |
| 群行动验证评分 | R+2 |
| 群行动、群服务奖励开始可领 | R+3 |

例如当前 phase 为 10 时，正在投票的是第 10 轮，正在加入的是第 9 轮，群行动正在验证第 8 轮，群行动与群服务可以结算第 7 轮。LP 此时已可结算第 8 轮。

参与数量按加入轮记录历史。未退出的参与会延续到以后轮次，不需要每轮重新转入资产。之后退出或追加只改变当前加入轮及未来快照，不改已经结束的历史轮次。奖励到达领取窗口后，当前实现没有额外的过期作废轮次。

## 4. 行动创建、提案与回调数据

提案以 `ActionTarget` 为目标时，`targetData[0]` 编码执行器地址。创建回调固定绑定，随后提交与投票回调必须匹配原执行器。行动可在以后的治理轮再次提交提案、获得该轮票数；历史绑定不会因此重建。

各执行器初始化参数如下，表中每个基础字段分别使用一个 `bytes` 项进行 ABI 编码。

| 执行器 | `targetData` 从索引 0 开始的内容 |
| --- | --- |
| LP | 执行器、LP 地址、治理占比倍数、首次加入最小治理占比；共 4 项 |
| 群行动 | 执行器、参与代币、每群激活质押、成员行动额度比例、激活最小治理占比、验证者申请质押、验证者惩罚比例；共 7 项 |
| 群行动可选资料 | 第 8 项编码 `(string[] keys, string[] descriptions)` |
| 群服务 | 执行器、来源行动代币、治理占比倍数、验证者奖励比例；共 4 项 |

群行动投票可以只支持行动，不指定验证者；若指定，则传 2 项：执行器、verifierId。只有分给该申请的有效非零票才增加它的票数。LP 和群服务投票没有额外业务参数。数组长度、基础字段的 ABI 字节长度及执行器绑定不符会拒绝交易，不应依赖解码后截断数据。

`ActionTarget` 本身不托管参与本金。执行器需要奖励时，通过它调用 core Mint，把该轮行动奖励发到绑定执行器，再由执行器分配。

## 5. LP 行动

### 5.1 资产和参与

LP 必须是 Stake 配置的 factory 登记的真实交易对，不接受任意 ERC20 冒充 LP。参与者授权执行器后，可加入、追加、部分取出或全部退出。首次加入检查最小治理占比，追加不重复套用首次门槛。

LP 本金保存在 `LpExecutor`。退出退还 LP，不将它拆成交易对的两种资产。当前成员和行动总量均有轮次历史。

### 5.2 当轮时间权重

在加入轮中途追加的 LP，不获得此前区块的参与权重。设本次新增量为 `a`，加入阶段起点为 `b0`，阶段长度为 `B`，加入区块为 `b`：

```text
新增扣减 d = min(a, floor(a × (b-b0) / B))
成员有效量 e = 历史参与量 - 该轮累计扣减
行动有效总量 E = 历史总参与量 - 该轮累计总扣减
```

部分取出按比例减少该轮已记扣减；全部退出清除该轮的参与量、扣减与新增记录。跨轮保留的数量在新轮没有前一轮的新增时间扣减。

### 5.3 奖励与治理上限

设行动奖励为 `Q`，成员有效占比 `l = floor(e × 1e18 / E)`：

```text
理论奖励 T = floor(Q × e / E)
最新治理占比 g = floor(成员最新治理票 × 1e18 / 最新总治理票)
治理占比上限 c = floor(g × 治理占比倍数 / 1e18)
```

- 倍数为 0 时关闭上限，实际奖励为 T。
- 启用上限时，若 `c >= l`，直接发 T，避免从已取整占比重算产生一单位误差。
- 若 `c < l`，发 `floor(Q × c / 1e18)`，T 与实际奖励的差额销毁。
- 启用上限且最新总治理票为 0 时，T 全部销毁。

参与数量、时间扣减和行动奖励属于历史奖励轮；治理占比使用领取时的最新 phase。未领取预估可随治理票变化，领取后缓存实际奖励、销毁量和治理占比，后续查询不再重算已领取结果。

## 6. 群行动：固定参数与群生命周期

激活质押和验证者质押使用行动所属社区代币 `tokenAddress`；成员参与和资助使用 `joinTokenAddress`，两者可能不同。

每群激活所需质押、验证者每份申请的质押在同一行动中固定。`maxJoinAmountRatio`、激活治理占比门槛不超过 `1e18`；验证者惩罚比例必须严格满足 `0 < P < 1e18`。这些参数不由群主事后修改。

群主激活群时缴纳固定激活质押并满足当前治理占比门槛。激活当轮不能停用；以后可停用、取回激活质押，再次激活时重新缴纳。停用会阻止新的加入和追加，但不会自动移除既有成员或抹掉他们的历史参与。

群配置包括：文案、群总容量 `maxCapacity`、首次最小参与量 `minJoinAmount`、单成员最大参与量 `maxJoinAmount`、最大人数 `maxAccounts`。最小参与量必须非零；单成员最大量若非零，不得低于最小量。各最大值为 0 表示不启用该项群级上限。

群主可更新激活群的配置。新配置约束之后的加入、追加；不会自动驱逐已存在的成员。文案有历史查询，`groupState` 中的其他配置是当前配置，不能把它当作任意历史轮的完整配置快照。

## 7. 群行动：成员额度、资产与资料

同一成员在同一行动中只能加入一个群，可以在不同的行动中加入不同群。成员总参与量是自有量与全部已用资助量之和。

加入或追加时同时检查群状态、单成员最大量和群总容量。最大人数及首次最小参与量只检查首次加入。除此之外，还有行动治理票决定的**单成员额度**：

```text
base = floor(joinToken.totalSupply × maxJoinAmountRatio / 1e18)
memberLimit = floor(base × 该行动本轮治理票 / 本轮治理总票)
成员自有量 + 全部已用资助量 <= memberLimit
```

`maxJoinAmount(token, action)` 查询的是这个成员上限，不能理解成整个行动的总参与容量；群总容量由 `maxCapacity` 约束。没有相应治理票时，不能凭群主放宽配置绕过该限制。

自有参与资产由成员转给执行器，部分取出或退出时退回成员。对未知外部参与代币，转入和退款边界校验接收方精确到账，非精确到账会使整笔交易回滚。参与代币就是本社区代币时，使用已知的无转账费路径，避免重复余额查询。这不代表兼容任意重基或恶意 ERC20。

验证资料 schema 固定于行动创建，最多 16 项；key、说明和成员 value 各最多 1024 字节。首次加入需提供完整资料；追加时传空数组表示保留原值，传完整数组则更新资料。资料按加入轮保存，验证者读取对应轮次，而非用最新资料覆盖历史。

## 8. 群行动：资助额度

资助者为指定群中的指定成员授权额度，并先将相应参与代币本金存入执行器。不能资助自己。新增额度要求群仍然激活，取回或撤销额度不要求群仍然激活。被资助者必须主动选择资助者并使用额度加入，授权本身不替其加入。

- 额度分为尚未使用与已经使用两部分，已用部分计入被资助成员的参与量。
- 被资助者退出时，全部已用资助恢复为资助者的可用额度，资金留在执行器。被资助者不能将资助部分直接取到自己钱包，也不能单独部分取出这部分资助。
- 资助者可取回未使用额度，也可撤销授权，连同已用部分收回；已用部分相应从成员参与量扣除。
- 若成员已无自有或其他资助参与量，清除其行动参与登记与群成员关系。
- 多个资助者的余额分别记账；返还一种来源的资金，不应消耗其他来源的本金。

成员查询可以分别看到自有量、资助量、来源资助者及其历史使用量。群和行动总量反映实际参与量，不把尚未使用的额度当成已参与。

## 9. 验证者申请：一份申请、一份质押

每个 `(token, action, verifierId)` 同时最多一份未撤回申请，拥有固定 applicationId 和一份质押。首次申请检查 NFT 所有者、行动存在、当前治理票非零及文案长度，并收取固定质押。

再次调用 `submitVerifierApplication` 修改仍可接票申请的文案时：

- applicationId 不变，不重复收押，不清票，不重置当选历史；
- 修改在下一投票轮生效，当轮及历史轮的文案保持不变；
- 同轮反复修改只覆盖尚未生效的下一轮文案；
- 已停止或存在逾期违约的申请不能借此恢复接票。

申请跨轮有效，选举票数按轮分别累计，不跨轮沿用。

## 10. 唯一验证者选举与历史

每轮最终得票最高且获得有效非零票的申请，是该行动该轮唯一验证者。票数相同时保留先达到该票数的领先者，不按申请 ID 抢占。无有效票则无验证者。候补、候补分时开放和首提交者锁轮机制均不存在。

链上在投票时维护当轮领先者：换人时，从旧领先者的当选历史末尾移除本轮，给新领先者追加本轮。过去轮次不再改变。当前轮记录只是潜在当选；投票期结束后自然成为最终结果，无需等待下一轮首票或其他结算交易。

`verifier(token, action, round)` 返回验证者 ID、申请 ID 和该轮票数；当前投票轮返回暂时领先者。`verifierElectedRounds` 分页返回已结束投票的最终当选轮次，不包含仍开放的当前轮。

## 11. 停止接票与撤回申请

`stopVerifierApplication` 立即停止该申请接收新票，不可恢复。停止不会删除已有票数、领先位置或当选历史，也不取消旧轮的验证权限与责任。

`cancelVerifierApplication` 才是结算、销毁罚款并退回余款的撤回入口。有尚未结束的责任时会拒绝，申请人可先单独停止接票；若已经没有待结束责任，可直接撤回，由该交易一并记录停止。

停止发生在 R 时，R 内不能完成退款后再申请。若 R 停止，之后 R+3 才退押，可以在 R+3 重新缴纳完整质押并获得新 ID，无需额外等待一轮。新申请与旧申请的责任分开，旧申请的记录不被清除。

当前轮仍领先者不能提前退押。即使下一加入阶段暂时无人，也不能认定永远没有任务：只有加入期结束后，才能确定该轮无需验证。已完成验证的旧责任不再阻止退押。

## 12. 履约、最近三次检查与扣罚

对某个当选轮 R，**同一轮同时满足以下三个条件**才算违约：

1. 加入期已结束，确实存在待验证成员；
2. 当前 phase 已到 R+3 或以后，验证期限已经结束；
3. 该轮全部验证尚未完成。

仍在 R+2 验证期内的任务不算违约。完整提交但分数全为零算履约；只提交部分群或部分成员算未完成。无任务的当选轮免罚。

每次接票前检查该申请最近三次实际当选，而不是最近三个日历轮。存在任何一次逾期违约就拒票，不依赖某笔先前的处罚交易，也不依赖罚款金额是否大于零。

为什么只需三次：若四次当选轮为 `R1 < R2 < R3 < R4`，则 `R4 >= R1+3`。接收第四次当选轮的新票之前，第一次已到期；若违约，就先被拒票，不能将该记录挤出最近三条。中间无人投票的空轮不改变此推理。正常完成任务的申请可长期当选，没有终身三次上限。

设该申请原始质押为 S，行动固定惩罚比例为 P，最近三次当选中的违约数为 F：

```text
处罚数量 = floor(S × P × F / (3 × 1e18))
退款数量 = S - 处罚数量
0 <= F <= 3，0 < P < 1e18
```

分母固定为 3，即使只当选一轮且违约，也只承担总比例的三分之一。按原始质押统一计算并一次取整，不对剩余质押连续乘比例，也不先将 P 除以 3。

| S=100，P=90% | 违约 0 轮 | 违约 1 轮 | 违约 2 轮 | 违约 3 轮 |
| --- | --- | --- | --- | --- |
| 销毁 | 0 | 30 | 60 | 90 |
| 退款 | 100 | 70 | 40 | 10 |

处罚金额和失败轮次由状态推导，不保存独立 `punished` 状态。尚在期限内的其他轮次之后可能违约，因此查询的金额是当前已确定部分；仍有潜在责任时不能提前取出余款。即使质押为零或金额取整为零，逾期记录依然阻止接票。

投票不会执行销毁。全部责任完成、确定无任务或到期后，撤回交易统一结算。申请人永不撤回时，质押保持锁定，罚款尚未实际销毁，申请仍不能再获得新票。

## 13. 验证过程与行动奖励

唯一验证者在 R+2 期间提交 R 的原始评分。每人分数为 0–100，每批最多 100 人，必须按该轮历史群成员顺序，从已验证游标连续提交，不能跳过、重复或覆盖已评分成员。过期轮不能补交；停止后的申请仍可提交尚在期限内的旧任务。

```text
成员最终分数 = 该轮成员自有及资助参与总量 × 原始分数
群最终分数 = 群内成员最终分数之和
整轮总分 = 所有参与群最终分数之和
成员奖励 = floor(行动奖励 × 成员最终分数 / 整轮总分)
```

所有参与群都验证完且整轮总分非零，才有可分配行动奖励。群权重按该群最终分数占比计算。已经验证但全部为零不会产生可领金额，也不因此处罚验证者。

没有候补意味着当选者不履约会使该行动该轮的全部参与者无法领取行动激励。下一轮仍可独立选举其他人，但不能补救已经过期的失败轮。质押数量与惩罚比例应按实际单轮违约成本评估：90% 的三轮上限，单轮成本是质押的 30%。

## 14. 群服务行动与资格

群服务不再自行评分，而是使用来源群行动已经完成的产出。服务奖励代币可以等于来源行动代币，也可以是其直接父代币；不能指定任意祖先或无关代币。

服务初始化固定来源代币、治理占比倍数、验证者奖励比例。验证者奖励比例严格大于 0、小于 `1e18`。加入服务只登记参与，不转入本金；加入者须在来源代币下拥有激活群，或在对应来源轮次具有验证者申请。加入资格不等于保证获得奖励，实际结算仍要求该服务轮有登记且有有效权重。

服务参与同样跨轮延续，退出改变当前加入轮及未来登记，不抹掉过去的合法领取资格。服务接口中的参与数量使用来源代币的群激活质押及其历史，不代表另缴了一份服务本金。

## 15. 群服务奖励公式与治理上限

对来源代币和轮 R，收集使用指定 `GroupActionExecutor` 的已投票群行动。设其中各行动的有效奖励为 A，只有整轮验证完成且总分非零的行动产生有效奖励。

```text
D = 所有这些行动有效奖励之和
V = 本成员作为唯一当选验证者的各行动有效奖励之和
O = 本成员对应群在这些行动所得有效奖励之和
Q = 本服务行动奖励池
p = 验证者奖励比例

验证者奖励 = floor(Q × p × V / (D × 1e18))
群主理论奖励 T = floor(Q × (1e18-p) × O / (D × 1e18))
```

同一个 memberId 可以同时获得两部分奖励。D 为零、无相应权重或服务奖池为空时，没有有效奖励可结算。

只有群主部分受治理上限约束。以**来源行动代币**的领取时最新治理票计算 g，`c=floor(g×治理倍数/1e18)`。当 `c >= ceil((1e18-p)×O/D)` 时发足 T；否则群主奖励为 `floor(Q×c/1e18)`，差额销毁服务奖励代币。倍数为零时关闭上限；启用上限而来源代币总治理票为零时，群主理论奖励全部销毁，验证者部分不受该上限影响。

首次真实铸出奖池后会按实际奖池重新计算。分母缓存按“来源行动代币＋轮次”隔离，只有该来源代币的对应轮奖励已准备时才缓存，不能因父代币服务先结算而过早冻结子代币的分母。已领取结果使用缓存，不随之后治理票变化。

## 16. 群主奖励二次分配

群主可为 `(sourceToken, sourceActionId, groupId)` 配置第三方成员、比例和备注，配置生效轮是当前验证轮 `phase-2`。同一验证阶段内可以修改该轮配置；进入领取阶段后读取已经结束的验证轮快照。

- 每个行动最多 8 名收款人；每来源代币／群最多 16 个非空收款配置行动；每条备注最多 256 字节。
- 收款 NFT 必须存在，不能是群主自身，不能重复；单项比例非零，总比例不超过 `1e18`。
- 只分配扣除治理溢出后的群主奖励，不分配验证者奖励。
- 先按来源行动中该群奖励占群主总权重切片，再按配置比例计算收款量。每步整数余数以及未配置比例均留给群主。
- 收款人无需加入服务行动，结算时直接转给相应 NFT 当前 owner。

`memberReward.mintAmount` 包含验证者奖励和完整群主奖励，也包含已经分给第三方的那部分，因此不等于调用者钱包的实际增量。展示群主实际到账应使用 `ownerRemaining + verifierReward`，并分别展示 `ownerDistributed`、`ownerBurned`。

## 17. 查询、公示与事件

查询大致分为三类，不应混淆：

| 类别 | 代表接口及含义 |
| --- | --- |
| 当前状态 | `groupState`、当前激活群与参与索引、`verifierStake`、`verifierApplications` |
| 历史事实 | `isJoinedByRound`、历史参与数量和资料、原始／最终分数、每轮验证者和票数、投票者名单、收款配置 |
| 待结算预估／已结算结果 | `memberReward`、`govRatio`、服务分配预估；未领取时可变，领取后以缓存为准 |

验证者当前列表包含所有未撤回申请，包括已经停止接票者；前端应使用 `stoppedRound`、`failedRounds` 判断是否还可接票。`pendingRound` 非零表示至少还有一个未结束的责任，返回其中一轮用于说明不能撤回的原因，并非完整待办列表；完整当选记录由 `verifierElectedRounds` 提供，当前领先情况由 `verifier` 提供。

`verifierApplicationsByRound` 返回轮末未撤回名册，并补上当轮有票后成功撤回的申请。先按历史集合顺序、再按当轮撤回归档顺序分页；这不是按票排序的榜单。零票申请同轮撤回不归档到该列表，但按成员的该轮历史查询仍可能找到它。停止本身不移除名册。

申请查询中的文案取所查询轮的快照；`stoppedRound`、`withdrawnRound`、`punishmentAmount`、`failedRounds` 和 `pendingRound` 反映当前已知事实。查询旧轮次不会假装回到过去尚未知道违约的时点。撤回后历史处罚仍可查询，新申请不覆盖旧轮票数和资料。

分页一般支持 `offset`、`limit`、`reverse`；`limit=0` 可读取总数，越界返回空页和真实总数。当前可删除集合使用交换末尾移除，不能把其位置当稳定排名。投票者名单按首次投票顺序保存，同一投票者追加票数不增加重复行。

创建、加入、退出、额度、选票、资料、评分、停止、退押、实际处罚和奖励分配均通过相应事件公示。处罚事件在撤回时产生，包含失败轮次和销毁量；在那之前，处罚预估应通过查询获得，不能依赖等待某个投票者触发事件。

## 18. 部署与兼容性

依赖来源为本仓固定的 core 及其嵌套依赖。部署顺序为：四个所需链接库、`ActionTarget(Mint)`、`LpExecutor(ActionTarget)`、`GroupActionExecutor(ActionTarget)`、`GroupServiceExecutor(GroupActionExecutor)`。库由工具链按链接需求部署；三个执行器从依赖关系推导 Stake、MemberNFT、Phase 等协议地址。

群行动没有候补部署参数、`SPLITS` 或 `run(uint256[])`；部署脚本使用 `run()`。行动业务数值在提案创建回调传入，不是通过新增管理员入口修改。

部署脚本广播前检查地址有代码，并交叉核对 Mint、Stake、Vote、Submit、Launch、factory 等依赖关系与 core 地址记录；广播后核对四个行动合约的绑定。独立检查脚本比较运行时字节码并处理 immutable 和链接库地址；源码验证脚本按实际构造参数编码。

本次验证者设计改变了公共 ABI、构造参数和内部存储布局，不兼容旧部署的原地存储替换。应部署匹配的新合约及库，并让新提案使用新执行器；不能把旧 ABI 与新地址混用。既有行动的绑定不会自动迁移，本文不提供转移旧部署资金或责任的管理员捷径。

## 19. 实现边界与运维关注点

1. 惩罚只针对是否按时完整提交验证，不证明评分客观正确；治理选人仍承担质量判断。
2. 唯一验证者可以让该行动一轮无法发奖，经济约束取决于实际质押、单轮罚款和受影响规模。
3. 未领取的 LP 与群主服务奖励使用最新治理票；补票能改变尚未结算的溢出，已结算结果不追溯。
4. 资助者能撤回已使用额度，成员不能把它当作不可撤销资助承诺。
5. NFT 转让会转移相关操作权与接收权。公示中的 ID 与地址不是永久一一绑定。
6. 预估之后状态仍可改变；链上执行时重新校验，前端不能把一次查询当作锁定报价。
7. 没有自动后台任务。时间推进会改变只读判断，转账、销毁和结算仍需要相应交易；处罚销毁只发生在撤回。
